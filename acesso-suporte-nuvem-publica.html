Antes de entrar em cada nuvem

Quatro perguntas que toda estrutura de nuvem responde

Onde o recurso vive?

A hierarquia define a que conta ou projeto um recurso pertence, quem paga por ele e até onde uma política se aplica.

Quem pode fazer o quê?

O IAM liga uma identidade (pessoa, grupo ou serviço) a um papel sobre um escopo. Menor privilégio é a regra.

Como eu sei que quebrou?

Auditoria e monitoramento registram quem fez o quê e quando. Sem isso, o suporte começa às cegas.

A quem eu peço ajuda?

O suporte tem planos, severidades e canais definidos. Saber usá-los bem reduz o tempo de indisponibilidade.

Os nomes mudam entre IBM Cloud e Google Cloud, mas as perguntas são as mesmas. Vamos respondê-las para cada uma.

Enterprise
Agrupa contas para faturamento consolidado e gestão centralizada. Nem toda organização usa; contas isoladas também funcionam.
Conta
Fronteira de IAM, faturamento e cotas. É onde usuários são convidados e onde políticas de acesso existem.

Como o acesso funciona

IAM: quem, com qual papel, sobre qual escopo

Sujeito
Usuário (IBMid), Service ID ou Trusted Profile
de preferência via access group
Política
Access policy
liga sujeito + papéis + escopo
Papéis
Plataforma e serviço
Viewer · Operator · Editor · Administrator / Reader · Writer · Manager
Escopo
Conta, resource group, serviço ou instância
quanto mais estreito, melhor

Identidades

  • Usuário — pessoa com IBMid, convidada para a conta (ou federada via IdP corporativo).
  • Service ID + API key — identidade para automações e pipelines; a chave é o segredo.
  • Trusted Profile — identidade assumida por workloads (clusters, VSIs) ou usuários federados, sem chave estática.
  • Access group — coleção de usuários e Service IDs; a política é dada ao grupo, não à pessoa.

Papéis: dois planos

  • Papéis de plataforma controlam o ciclo de vida do recurso: criar, apagar, ver, atribuir acesso.
  • Papéis de serviço controlam o uso do serviço: ler um bucket, escrever numa fila, gerenciar chaves.
  • Um mesmo usuário pode ser Viewer na plataforma e Writer no serviço.
  • Boas práticas: grupos por função, escopo por resource group, revisão periódica de chaves e Service IDs.
Onde ver: Console → Manage → Access (IAM). Auditoria de quem fez o quê: IBM Cloud Logs (Activity Tracker events).

Como conseguir acesso na Caixa

Três passos até o seu perfil ficar completo

1 · Acesso Lógico
Solicite o grupo CLOUD_IBM_PRODUCAO_SUPORTE
na plataforma Acesso Lógico da Caixa — é o que libera a entrada na conta
2 · FICUS no SISGSC
Abra uma FICUS pedindo as permissões adicionais
complementa o perfil com os access groups específicos da sua função
3 · Login federado
cloud.ibm.com/authorize/caixa_tem
sempre por este link; ele autentica você com as credenciais Caixa

O que acontece por trás

  • O grupo do Acesso Lógico corresponde a um access group na conta IBM Cloud — é a política base, comum a todo o time de suporte de produção.
  • A FICUS é o registro formal das permissões extras: sem ela, você entra na conta mas não enxerga tudo o que precisa.
  • Se um link da IBM Cloud abrir sem os seus recursos, você provavelmente não está logado pelo /authorize/caixa_tem.

Antes de pedir

  • Confirme com a liderança técnica quais permissões adicionais a sua função exige — a FICUS deve listá-las de forma objetiva.
  • Guarde os números das solicitações (Acesso Lógico e FICUS): eles são o histórico do seu perfil.
  • Tudo o que envolve IBM Cloud na Caixa está documentado na wiki: wiki.suporte.caixa/index.php/IBM_Cloud.
Acesso Lógico e SISGSC são plataformas internas da Caixa; o link de login é o ponto de entrada federado da conta IBM Cloud da Caixa.

Ferramentas do dia a dia

Quatro portas de entrada para a mesma conta

Console
Entre por cloud.ibm.com/authorize/caixa_tem. O seletor de conta no topo define onde você está: confira conta e resource group antes de criar qualquer coisa.
CLI
ibmcloud login --sso (federado) · ibmcloud target -r <região> -g <rg> · plugins por serviço (is, ks, cos).
Terraform
Provider IBM-Cloud/ibm, autenticado por API key de Service ID. Todo recurso recebe resource_group_id explícito.
API
Token IAM obtido a partir da API key; mesmas políticas do console. Útil para integrações e scripts.

O que observar

  • Monitoramento centralizado — cloud.ibm.com/observability/monitoring reúne os principais serviços da Caixa em um só lugar. Faça login pelo /authorize/caixa_tem antes, senão o link não carrega os seus dados.
  • IBM Cloud Logs / Activity Tracker — eventos de gerenciamento: quem criou, alterou ou apagou. Primeiro lugar a olhar em incidente.
  • Notificações da conta — manutenções e incidentes planejados chegam por e-mail para quem tem a preferência ativada.
  • Status page — cloud.ibm.com/status: verifique antes de abrir caso.

Acesso privado

  • Virtual Private Endpoints (VPE) — serviços da IBM alcançados pela rede privada da VPC.
  • Direct Link — conectividade dedicada entre o datacenter e a IBM Cloud.

Conta de faturamentoFica fora da árvore: cada projeto é vinculado a uma billing account. Sem vínculo, as APIs pagas não funcionam.
Políticas da organizaçãoRestrições (Org Policy) descem pela árvore: domínios permitidos, regiões, IPs externos, chaves de service account.
Organização
Nó raiz de tudo. Existe uma por domínio corporativo; políticas e papéis aqui valem para toda a empresa.
Pasta
Agrupa projetos por área, ambiente ou time. Pode aninhar. É o lugar natural para políticas de IAM compartilhadas.
Projeto
Unidade de trabalho: habilita APIs, tem cotas, IAM e faturamento próprios. O ID é imutável; o número identifica o projeto nas APIs.
Recurso
Vive dentro de um projeto e pode ser global, regional ou zonal — a localização muda o que é possível ligar a quê.
Nome completo de um recurso: //compute.googleapis.com/projects/<id>/zones/<zona>/instances/<nome> — projeto e localização sempre aparecem.

Como o acesso funciona

IAM: principal, papel, recurso — e a herança pela árvore

Principal
Usuário, grupo Google, service account ou identidade federada
de preferência via grupo
Vínculo
Allow policy (binding)
principal + papel + condição opcional
Papel
Básico, predefinido ou personalizado
ex.: roles/compute.viewer
Recurso
Organização, pasta, projeto ou recurso individual
herda para tudo abaixo

Identidades

  • Usuário — conta corporativa no Cloud Identity / Workspace (normalmente federada com o IdP).
  • Grupo Google — o que recebe papéis; pessoas entram e saem do grupo, não das políticas.
  • Service account — identidade de workloads e automações. Prefira anexar ao recurso; evite chaves JSON.
  • Workload Identity Federation — pipelines externos (ex.: GitHub, outra nuvem) assumem uma identidade sem chave estática.

Herança e cuidados

  • Um papel na pasta vale para todos os projetos dela; um papel na organização, para tudo. A política efetiva é a união.
  • Papéis básicos (owner, editor, viewer) são amplos demais para produção — use predefinidos.
  • Deny policies e Org Policy bloqueiam mesmo quem tem permissão concedida.
  • O IAM Recommender sugere reduções de permissão com base no uso real.
Onde ver: Console → IAM e administrador. Auditoria: Cloud Audit Logs (Admin Activity sempre ligado; Data Access sob demanda).

Ferramentas do dia a dia

Quatro portas de entrada para o mesmo projeto

Console
console.cloud.google.com — o seletor de projeto no topo define onde você está. Confira o projeto antes de criar qualquer coisa.
gcloud
gcloud auth login · gcloud config set project <id> · gcloud auth application-default login para SDKs e Terraform locais.
Terraform
Provider hashicorp/google. Em pipeline, autentique com service account impersonada ou Workload Identity Federation, nunca com chave no repositório.
API
Toda ação do console é uma chamada de API que precisa estar habilitada no projeto. "API not enabled" é o erro mais comum de quem chega.

O que observar

  • Cloud Audit Logs — quem criou, alterou ou apagou, no Logs Explorer. Primeiro lugar a olhar em incidente.
  • Cloud Monitoring — métricas, alertas e uptime checks; dashboards por projeto ou por escopo de métricas.
  • Personalized Service Health — incidentes do Google que afetam os seus projetos, com alertas.
  • Status dashboard — status.cloud.google.com: verifique antes de abrir caso.

Acesso privado

  • Private Google Access / Private Service Connect — APIs do Google pela rede privada da VPC.
  • Cloud Interconnect — conectividade dedicada entre o datacenter e o Google Cloud.
